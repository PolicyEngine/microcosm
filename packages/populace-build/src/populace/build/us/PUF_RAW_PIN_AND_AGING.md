# IRS PUF raw pin and Populace aging design

## Decision

Neither `puf_2015.h5` nor `puf_2024.h5` is raw microdata. Both are processed
PolicyEngine entity-array exports. The true tax-return source is the
access-controlled IRS 2015 PUF CSV, with a separate demographic supplement
used by the retired personization pipeline.

Populace can own the raw-column aging engine now, and this change adds that
engine. The production input cannot yet move to raw bytes because the
restricted upstream declaration has no immutable revision or certified
content hash, the Ledger bundle lacks the full historical and target-year
factor surface, and the bespoke support builder still accepts only processed
root-array HDF files.

No row-level values are recorded in this document.

## Tax-unit source versus retired personization

The raw CSV contains four disclosure aggregate records (`RECID` 999996-
999999, `MARS == 0`). Release 1.8.0 drops those four records and exports
207,692 tax units. Current Populace source logic instead declares
deterministic donor-template disaggregation. That is an intentional
row-topology policy, not an exact replay of the release.

For each non-aggregate raw return, the retired processed person count is
exactly:

```text
1 + (MARS == 2) + min(3, max(0, XTOT - 1 - (MARS == 2)))
```

This identity matched all 207,692 release tax units. The random `EARNSPLIT`
filer/spouse allocation also cancels when processed person arrays are grouped
back to tax-unit totals. Populace therefore does not need
`demographics_2015.csv`, the retired demographic QRF, or `EARNSPLIT` merely
to construct a tax-unit donor.

As an audit, 56 processed financial outputs were reconstructed at tax-unit
grain from raw fields. All matched, with maximum relative residual
`1.82e-16`. This verifies raw-field lineage without committing microdata.

## What the release aging actually did

The physical release was generated by tag `1.8.0`, commit
`371f77a0aadfdeacd5856e0a3030c2db0eda65b5`. Its
`datasets/puf/uprate_puf.py`:

1. ages selected fields from 2015 to 2021 by SOI per-return growth;
2. applies distinct positive and negative growth to three signed fields;
3. applies a fixed 2% annual rule to five itemized fields;
4. applies adjusted-gross-income growth to a fallback list;
5. scales `S006` by the all-return count ratio.

It accidentally owns `E00900` and `E26270` twice: once in signed rules and
again in the fallback list. The effective factors therefore multiply both
steps. The full ordered ownership map and exact factors live in
`puf_aging_archived_1_8_0.yaml`.

The intended processed-array 2021-to-2024 leg applies nothing.
`create_policyengine_uprating_factors_table()` returns a table indexed by
variable with integer years as columns. The generator loops over those
columns as though they were variable names, and no integer year matches a
string array key. `puf_2024.h5` is consequently 2015-to-2021-aged content
labeled 2024.

### Derived component identities

Derivation must follow raw-column aging so a semantic copy is not aged
independently from its components:

```text
nonqualified dividends
  = aged(E00600) - aged(E00650)

tax-exempt pension income
  = aged(E01500) - aged(E01700)

rental income
  = aged(E25850) - aged(E25860)

estate income
  = aged(E26390) - aged(E26400)
```

The physical release's tuition is aged `E03230` only. Later commit
`42ed5d45...` changed the derivation to
`max(aged(E03230), aged(E87530))`; that is prospective Populace logic, not
physical-release parity. The physical release's old QBI W-2 proxy is exactly:

```text
0.16 * max(
    0,
    aged(E00900) + aged(E26270) + E02100 + aged(E27200),
)
```

## Landed aging engine

`us_runtime/puf_aging.py` provides:

- immutable, versioned factor and provenance objects;
- strict JSON/YAML-compatible parsing;
- exclusive ownership checks, including rejection of a field listed in two
  factor families;
- straight, signed-positive, signed-negative, and weight scaling;
- fail-closed checks for missing, nonnumeric, or nonfinite named columns;
- preservation of declared structural/unchanged fields;
- aggregate provenance in `DataFrame.attrs`, including factor-source digest,
  fact IDs, years, fallback columns, and row count.

`us_runtime/source_runtime.py` now registers the manifest `uprate` handler.
The handler requires:

- `from_year` from the manifest;
- `target_year` from build configuration;
- an explicit `aging_version`;
- an explicit factor bundle supplied under the named runtime-config key.

Version or year mismatches and a missing factor bundle fail closed. The source
manifest orders raw handling as:

```text
read raw table
  -> disaggregate disclosure aggregates
  -> age raw columns
  -> derive PolicyEngine-aligned columns
  -> fit the donor model
```

The packaged `archived_1_8_0` profile is audit-only and supports exactly
2015-to-2021. It preserves the retired double-aging bug and release-tag
`E87530` omission. The manifest names a future `ledger_v1` production bundle;
none is silently substituted when that bundle is absent.

## Production pin migration

The processed HDF locator can be removed only after these steps are complete:

1. Certify the licensed raw repository revision and the two CSV content
   digests, or require caller-supplied bytes that match an approved digest.
2. Make the production builder read the raw tax-return table and verify its
   schema/digest before transformation.
3. Apply the reviewed aggregate-record policy. Record explicitly that
   disaggregation differs from release 1.8.0's four-row drop.
4. Construct a `ledger_v1` bundle from immutable Ledger facts for the source
   and active target years. Assign each raw field once and record every
   fallback.
5. Age raw E/P/T fields and `S006`, then re-run semantic derivations.
6. Run `qbi_simulation_version=1` after target-year business-source
   construction.
7. Adapt the resulting tax-unit source frame to the existing weighted donor
   path and close every required output.
8. Persist the raw digest, factor-bundle digest/fact IDs, aging version,
   target year, QBI version, and aggregate diagnostics in release provenance.

## Blocking items

- **Immutable licensed source**: archived download declarations have
  `revision=None` and `sha256=None`. The observed local hashes need
  certification under licensed access.
- **Ledger factor coverage**: a production bundle needs 2015 endpoints and
  active-target-year facts/series for all-return count, AGI, wages, interest,
  dividends, signed business/partnership/capital-gain legs, retirement,
  unemployment, and Social Security. The local bundle has recent SOI facts,
  not this complete surface.
- **Target-year policy**: the archived second leg is a code no-op; there is no
  trustworthy 2021-to-2024 model to recover. Production must define corrected
  build-year factors instead of relabeling 2021 values.
- **Builder ingestion**: `tools/build_us_puf_support_base.py` still requires
  `--puf-h5` and reads processed root arrays directly. It does not execute the
  raw source manifest.
- **Incomplete donor surface**: QBI v1 closes 14 missing leaves, but the
  exact processed artifact remains short ten non-QBI outputs: mortgage-only
  interest, unreimbursed employee expenses, farm operations, partnership
  self-employment earnings, and six mortgage-structure leaves.
- **Runtime tail**: the generic source registry still lacks the declared
  `fit_weighted_qrf` implementation, and the manifest's aggregate
  `support_clip` declaration does not match the existing single-output
  numeric clip handler.
- **Raw-to-donor adapter**: production needs a reviewed tax-unit-frame adapter
  and output reconciliation before the processed HDF can be retired.

These blockers are integration work, not reasons to retain retired
derivations as governing inputs.

## Ready-to-paste PR-body summary

The truly raw 2015 PUF source is the restricted 207,696-row IRS tax-return
CSV, with a separate demographic supplement used only by the retired
personization pipeline; both staged HDF files are processed entity exports.
This change adds a pure, versioned raw-column aging engine and a fail-closed
manifest handler. An audit-only `archived_1_8_0` profile exactly reproduces
the release's 2015-to-2021 factors, including distinct signed legs, the fixed
itemized rule, the AGI fallback, and accidental double scaling of `E00900`
and `E26270`. It does not claim genuine 2024 aging: the retired 2021-to-2024
loop was a no-op. The production manifest reserves `ledger_v1`, which must be
supplied from certified raw bytes and immutable Ledger facts. The actual raw
pin switch remains blocked on licensed-source certification, target-year
factor coverage, the builder's HDF-only ingestion seam, and completion of the
remaining donor contract. Refs #530.
