Microcosm can publish a release build into its own folder through the emitter. The new `microcosm-publish-release-build` command (`microcosm.build.release_publication`, in `microcosm-build`) checks a UK national, dense or local-area build in the build-folder layout with the release contract and hands every file to the separately installed `microcosm-emitter` with the interface's `publish_release` call, which writes `releases/<release>/<build>/` and the repository's `releases.json` in one commit; `--make-current` and `--promote` change the current build, which counts only when the emitter's receipt is `published` and names it as `current`. The command refuses before any emitter starts while the repository has any `latest*.json` pointer file, or with `HF_HUB_OFFLINE` or `TRANSFORMERS_OFFLINE` set, and hands nothing over unless the emitter's write-access check passes; `microcosm-publish-release` refuses a repository that has `releases.json`. Build-folder manifests name `release` and `build` as strings, record `built_at`, `built_with_model_package` and `built_with_core_package` at the top level and a `role` on each artifact, and pin no `revision`. For a registry entry that names a release (UK 2025 national and dense), `microcosm.data.load` reads the current build from `releases.json` where the repository has one, or the listed build `build=` names, and follows the pointer file exactly as before where it does not. The stable releases proposed for US builds, `populace-us-2024-national` (`national`, the default) and `populace-us-2024-local` (`local_area`), are recorded in `microcosm.data.contract.PROPOSED_US_RELEASES` but not used until they are agreed with the US data builder.
