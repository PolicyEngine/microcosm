In a checkpointed US base run (`tools/build_us_puf_support_base.py --stage all`), the step processes no longer hash the PUF H5, the PUF CSV, the builder's source files, the pinned ASEC files or the `block_v1` location ladder. Before, each step process (24 under the default location rule, 23 under `block_v1`) hashed the PUF and source files again to compare its run config with the one locked in the checkpoint directory, and the location ladder too under `block_v1`. With `--asec-h5-sha256` pins, each also hashed every pinned ASEC file to compare it with its pin. Now the parent does both checks once. It then passes each step process the SHA-256 of each of those files, keyed by the file's resolved path, and the source digest, with the repository root and tool file it covers, in the environment variable `MICROCOSM_US_BASE_PARENT_DIGESTS`. A step process uses a digest only for the same path, and only when its own parent set the variable. It hashes every other file itself, so a named `--stage` run by hand without the variable hashes everything as before. A malformed variable stops the step. Two steps still check the ASEC bytes they read. `household_location_assignment` (`block_v1`) hashes the pinned ASEC files itself. `source_construction` compares the digests of the bytes it read with the pins, as before. `clone_feature_extraction` still hashes both PUF files for its own metadata. `microcosm.build.code_identity.builder_code_identity` takes the source digest as `source_sha256` and then reads no source file. The recorded run config is unchanged, so existing checkpoint directories still resume. A resume after a PUF file, a pinned ASEC file, the ladder or the builder's code changed is still refused before any step process starts. A step process no longer notices one of those files changing while the run is under way, a `git pull` in the same checkout included. Written outputs are unchanged.
