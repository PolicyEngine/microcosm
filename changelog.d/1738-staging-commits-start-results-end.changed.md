Staging run files (`runs/<run_id>/` in the Hugging Face staging repositories) are handed to the build's emitter at three points only: when the run starts, when a result file is added and when the run ends. Every hand-over is forced and carries the run's folder as it stands, so the folder exists from the run's start and the emitter commits each hand-over at its next cycle. Stage events and calibration progress in between are still written locally and reach the repository with the next hand-over; the build's hosted telemetry is the live record of a running build. `--staging-upload-interval-seconds`, the writers' `upload_interval_seconds` (and version 2's `monotonic`), `force_upload` on `stage`, `attach_artifact` and `add_artifact`, and the US build record's `staging_settings.upload_interval_seconds` are removed; US certification ignores that field in older records.

Once a remote run has completed, failed or been refused by its release checks, the build has the emitter read its final commit back (up to 120 seconds, or 30 after a SIGTERM) before it reports the run's outcome, and reports the result to its hosted telemetry as a `staging_final_commit` stage. A failed check warns and changes neither the build's outcome nor the run's delivery summary; with `--staging-read-back` (UK builds) the check is that stricter read-back, which still fails the build. The US writer (staging version 1) now pauses after three refused hand-overs instead of stopping for good, and hands its final state over on completion and failure, as the UK writer already did. A SIGTERM in the US fiscal refresh build (`tools/build_us_fiscal_refresh_release.py`) closes its staging run as failed, records a termination with the emitter and exits 143, as UK builds already do.
