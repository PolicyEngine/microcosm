The primary-QRF worker identity (`worker_identity.py`) and the older binding in `stacked_spine.py` record the same value, and the identity's cache now keys an unset variable by that value. Both label that fallback `resolution: "joblib_cpu_count_fallback"`; identities recorded before carry `"os_cpu_count_fallback"` and still validate. The frozen schema-4 worker shape that the scoring-only relocation of schema-9 pools compares with their sealed records reports an unset count as that code recorded it, the host's `os.cpu_count()` under the old label, so that comparison is unchanged. A `LOKY_MAX_CPU_COUNT` that is not an integer, which joblib refuses, now fails with an error naming it. Fit jobs keep `n_jobs=-1`, which joblib already resolves to `joblib.cpu_count()` threads, so chain states and run configurations record what they did before. Draws are unchanged: new tests require byte-identical draws for one and four prediction workers and for one and four fit jobs, for a single-forest target, a target with zero, positive and negative values, and a target-at-a-time chain.
