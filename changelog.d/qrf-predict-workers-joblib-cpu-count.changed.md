Size the QRF draw's thread pool from the CPUs the process may use, and stop treating QRF thread counts as something a pool load or a resume must match. With `POPULACE_FIT_PREDICT_WORKERS` unset, the pool now has `joblib.cpu_count()` threads (`microcosm.fit.qrf.default_predict_workers`), the smallest of the machine's CPU count, the process's CPU affinity mask, a Linux cgroup CPU quota and `LOKY_MAX_CPU_COUNT`, and 1 when joblib has turned multiprocessing off, instead of `os.cpu_count()`, which counts only the machine's CPUs: a container held to a CPU quota no longer starts one thread per host CPU. The variable still overrides the default. Fit jobs keep `n_jobs=-1`, which joblib already resolves to `joblib.cpu_count()` threads, so chain states and run configurations record what they did before. A `LOKY_MAX_CPU_COUNT` that is not an integer is refused by joblib; the draw's pool sizing and the worker binding report it by name. Draws are unchanged: new tests require byte-identical draws for one and four prediction workers and for one and four fit jobs, for a single-forest target, a target with zero, positive and negative values, and a target-at-a-time chain.

The primary-QRF worker binding (`worker_identity.py`, now schema 2) records `POPULACE_FIT_N_JOBS` and `POPULACE_FIT_PREDICT_WORKERS` in a new `audit_thread_controls` field next to the interpreter paths in `audit_aliases`, and no longer in its semantic identity. Loading a pool for release or scoring, resuming the primary-QRF checkpoint, the pool's checkpoint identity and the spec engine's worker resolution compare only the semantic identity, so a pool built with one pair of counts loads under another, whether the counts come from the machine or from the two variables. Building the binding still refuses a malformed count. An unset prediction-worker count is recorded as `resolution: "joblib_cpu_count_fallback"`; `"os_cpu_count_fallback"` still validates. Schema-1 bindings still validate, and a pool that holds one is refused because its worker identity changed. The semantic identity is now cached per lock only. The spec template for the worker binding (`imputation.yaml` and `imputation.schema.json`) names schema 2 and the new field. The frozen schema-4 shape that the scoring-only relocation of schema-9 pools compares with their sealed records keeps the counts where that code recorded them, an unset count as the host's `os.cpu_count()`, so that comparison is unchanged and still includes the counts. The unused older binding in `stacked_spine.py` records the joblib default under the new label.

A resume no longer compares `POPULACE_FIT_N_JOBS`. `QRF.fit_draw_next` accepts a chain state that recorded another count, and `QRFChainState` equality ignores the count; the state still records the value in force when the chain started, so saved states keep their bytes. The ACS transfer target bank checks a saved target's predecessor digest with the count that target saved, so it reuses the target where it used to rebuild it. The PUF support base builder records both QRF thread variables in its run configuration and no longer compares them on resume (`StageRuntime`'s new `resume_ignored_run_config_paths`); the BLAS and OpenMP thread counts and `PYTHONHASHSEED` stay compared. A base run or pool build interrupted before this change cannot resume after it, because its recorded worker identity hashes the edited `qrf.py`, `worker_identity.py` and `stacked_spine.py`.
