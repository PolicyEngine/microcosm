A build's telemetry sends no longer wait for the shared local spool. Before, the emitter service appended each event to the SQLite spool before replying. When another build held the spool's write lock, a send waited up to SQLite's 5 s busy wait while the build's client gave up after 0.2 s and printed "could not queue an update", and an append still locked after 5 s dropped the event. Now the service replies once the event is queued in memory, and one writer thread appends queued events in arrival order, up to 100 per transaction, retrying lock errors for as long as they last. Heartbeats and the record of a killed build go through the same queue, so the killed-build record follows every event the build sent.

The queue holds at most 10,000 events and 16 MiB of their encoded JSON, with 16 events and 256 KiB kept for run events (started, completed, failed), so a queue that progress updates have filled still records how the build ended. A full queue refuses updates and prints one warning line. When the build closes or dies, the service spends up to its 15 s drain writing the queue, starts no append in the last 0.25 s of it, and reports in one line how many events it could not write.
