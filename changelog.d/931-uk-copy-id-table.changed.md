The UK spine mints every copy row's ids from fixed decimal fields declared in `microcosm.build.uk_runtime.copy_id_table`, not from a power of ten above the largest id each copy layer sees (#931). Once the spine clones households at its start, that largest id would grow with the clone count K, so every layer's offset would move with K and the K=1 spine would stop being the clone-0 slice of the K=15 spine. Copy `k` in a field takes `id + k × radix` on all five id columns, so every copy id is a function of its source id and its copy path alone. The fields, least significant first: `vintage` (10 ordinals at 10^8, reserved for pooled FRS vintages, minted by nothing yet), `geographic_support` (100 at 10^9, for the clone-first spine), `spi_support_channel` (3 at 10^11: the SPI copy at 1, the income band donor at 2), `high_value_support` (6 at 10^12), `cgt_support_split` (10,000 at 10^13), `cgt_incidence_clone` (2 at 10^17) and `cgt_residential_split` (8 at 10^18, the top field). The largest mintable id is about 7.2e18, below int64's limit, which the module checks when it loads.

- **Where.** `frs_spine` refuses raw ids at or above 10^8. The SPI support channel, the income band donors (whose sources are now read from their `{entity}_source_id` columns), the high-value split, the CGT support split, the incidence twin and the residential arms mint through the table, which refuses an ordinal outside its field, a row that already carries one and an int64 overflow. The CGT split refuses a household that would need more than 10,000 copies with a fixed message. The incidence anchor pairs each twin with the id less the twin field's radix, whatever the frame's largest id. The executor recovers each id-offset stage's parents at the stage's declared radix, refuses an incumbent id at or above it, and reads ids as exact int64 rather than row by row, which upcast an all-numeric row to float64. Refusals print counts, never ids.
- **What moves.** Base FRS rows keep their ids. Every copy row's five id columns change: SPI copies by +10^11, band donors by +2×10^11, high-value copies by k×10^12, CGT copies by k×10^13, twins by +10^17 and arms by j×10^18. Relative id order is unchanged at K=1, so sorts, ties, ranks and folds are unchanged. Values move on copy rows through every draw keyed on the copy's own id: the SPI income stage's second stage, stages 19 to 24 and 27 to 41, every twin's Advani-Summers prior (so the CGT gains layer is re-realised), stages 48 to 54 and policyengine-uk's Warm Home Discount draw on copy households in spine engine calls. Base rows move second-order through pooled steps: the high-value selection, the regional value ranks, the landlord walk, the residential solve, the anchor, the CGT walks and calibration. Draws keyed on `person_source_id` do not move. National ids now pass 2^53 from the CGT support split on.
- **Dense line.** The dense expand keeps its multiplier above the spine's largest id, which a table-minted spine's twins and arms leave no room above: a dense pool with more than one clone is refused at every entry point (the graph's `uk.full.expand`, the ladder and crosswalk clone routes and the row-wise tool's plans) in one message naming #931 and the clone-first spine. Dense builds with K > 1 wait for #931's clone-first spine; K = 1, and a spine without copy rows, expand as before.
- **Declarations.** The `id_remapping` texts of the copy stages in `sources.yaml`, `source_stages.json` and the code dictionaries name the table field; the SPI support and band-donor operations gain the key, which the source schema now requires. The stages that read the table bind it into their hashes, and the SPI support, band-donor, high-value and CGT clone and anchor stages also bind the helper modules they call. Every spine node re-keys; the coverage manifest's source digests and the H2 fixture are regenerated.
