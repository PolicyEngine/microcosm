The build stage profiler (`microcosm.build.stage_profile.profile_stage`, which writes `stage_profile.json` for each US base step and QRF variable) no longer starts a `ps` process every 0.25 s where `/proc` is unreadable, as on macOS. There it takes the entry and exit readings as before (one `ps` call each, falling back to `ru_maxrss` where running `ps` raises `OSError`, exits non-zero or times out), and reads the process's lifetime peak resident memory (`getrusage(RUSAGE_SELF).ru_maxrss`) just after each of them. The recorded peak is the later `ru_maxrss` reading or, if that is lower, the larger of the entry and exit readings. On a 60 s step on a 10-core Mac this cuts the profiler's CPU time from about 1.1 s (1.8–1.9% of one core, about 210–230 `ps` runs) to 0.015 s. Each record gains `peak_rss_source`:
- `sampled_current_rss`: `/proc` was read in the background at least once, as before (Linux, including Modal).
- `process_peak_rss_reached_during_stage`: `ru_maxrss` rose during the stage, so the peak is the stage's own.
- `process_peak_rss_reached_before_stage`: `ru_maxrss` did not rise, so the stage's own peak is at most the recorded value. On macOS that happens when startup, imports or an earlier profiled stage in the same process used more memory. On Linux, `ru_maxrss` can also hold the parent process's peak.
- `entry_and_exit_rss`: nothing between the entry and exit readings was measured (no background sample was taken, or `getrusage` gave no usable value), so the peak is the larger of those two readings.

`stage_profile.json` stays at schema version 1, so a resumed run merges new records into a file an earlier run wrote; records from before this change lack `peak_rss_source`. No data output changes.
