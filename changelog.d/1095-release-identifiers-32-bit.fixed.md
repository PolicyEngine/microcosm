A UK release's identifiers stay inside the range policyengine-uk stores (microcosm#1194, microcosm#1095; uk-data#558 is the incumbent's side). The clone stages number each copy by adding a power of ten to every identifier, so a built frame's identifiers run far past 2,147,483,647, and policyengine-uk keeps its five identifier variables as 32-bit integers: the stored values wrapped, so `calculate("household_id")` did not return the file's identifiers and every engine draw keyed on one read the wrapped number. The release boundary now renumbers (`national_frame.uk_release_identifier_tables`, called by `uk_release_export_frame` and by the local export): per entity the identifier is one plus the rank of the build identifier, the person table's two memberships map through the same arrays, and row order does not change. The build identifiers stay in the file as `person_build_id`, `benunit_build_id` and `household_build_id`, which the existing lineage columns describe, and are allow-listed on the export surface. The build and its checkpoints keep the build identifiers, because every draw in the build is keyed on them. The engine file the calibration measures on carries the release's identifiers (a per-clone block takes the ranks its rows have in the whole frame), so the solve fits the engine outputs the released file gives. Both readbacks refuse a written identifier that repeats, is below 1 or is above the 32-bit range, naming the column only. The release assembler pairs a release with its spine on the build identifiers, and the size evaluation and `tools/verify_uk_identity_stability.py` read them too. Engine tests hold both halves against the installed engine: the renumbered file's identifiers read back as written, and the build's own do not. Why the calibration follows: policyengine-uk spreads each person's birth month over the year by a hash of `person_id` (`months_since_last_birthday`), and the date of birth decides the two-child limit, the State Pension scheme and the Pension Credit qualifying age. Measured on a calibrated file, with the solve left on the build identifiers, the renumbered file moved two-child-limit and Universal Credit award rows by up to a tenth or more against the solve's own estimates; the receipts give the comparison. The Universal Credit deduction draws do not move: the build stores them. The spine stages still read the engine on the build identifiers, as before.
