A UK release's identifiers stay inside the range policyengine-uk stores (microcosm#1194, microcosm#1095; uk-data#558 is the incumbent's side). The clone stages number each copy by adding a power of ten to every identifier, so a built frame's identifiers run far past 2,147,483,647, and policyengine-uk keeps its five identifier variables as 32-bit integers: the stored values wrapped, so `calculate("household_id")` did not return the file's identifiers and every engine draw keyed on one read the wrapped number. The release boundary now renumbers (`national_frame.uk_release_identifier_tables`, called by `uk_release_export_frame` and by the local export): per entity the identifier is one plus the rank of the build identifier, the person table's two memberships map through the same arrays, and row order does not change. The build identifiers stay in the file as `person_build_id`, `benunit_build_id` and `household_build_id`, which the existing lineage columns describe, and are allow-listed on the export surface. The build, its checkpoints and the engine scratch file keep the build identifiers, because every draw in the build is keyed on them. Both readbacks refuse a written identifier that repeats, is below 1 or is above the 32-bit range, naming the column and a count. The release assembler pairs a release with its spine on the build identifiers, and the size evaluation and `tools/verify_uk_identity_stability.py` read them too. Engine tests hold both halves against the installed engine: the renumbered file's identifiers read back as written, and the build's own do not. Consequence: policyengine-uk spreads each person's birth month over the year by a hash of `person_id` (`months_since_last_birthday`, which the State Pension age and Pension Credit qualifying-age tests read), so it deals those months on the release's identifiers, where the calibration's scratch file dealt them on the wrapped build identifiers; the receipts measure the difference. The Universal Credit deduction draws do not move: the build stores them.
