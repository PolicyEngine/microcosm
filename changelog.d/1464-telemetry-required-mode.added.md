A build that must send telemetry can say so with `MICROCOSM_TELEMETRY_REQUIRED=1` (microcosm#1464). Only builds that start the emitter adapter read it: the UK full and spine builds and the US fiscal refresh build; the registered US Modal programs do not start the adapter yet and ignore it. Starting its emitter then raises `TelemetryRequiredError` (`microcosm.build.telemetry_emitter`), so the build exits nonzero before doing any work, when the emitter cannot be prepared, the `microcosm-emitter` command is missing, its `version` times out or fails, it is older than `MINIMUM_EMITTER_VERSION`, it lists no protocol version 1, its `hello` fails, it exits or times out before it is ready, or it starts without its telemetry module. The error names a fixed reason, the exit code where there is one and, for a missing or outdated emitter, the install or upgrade command; it never holds a setting's or credential's value. For the failures the adapter finds before anything starts, nothing says the build continues. For a failure `EmitterClient.start` reports itself, interface 0.7.0 first prints "Local Microcosm emitter failed to start (<reason>); the build will continue.", and the error says that line does not apply. Emitter 0.11.0 and later exit before they are ready when the collector-token variables they inherit (`MICROCOSM_COLLECTOR_TOKEN`, `MICROCOSM_COLLECTOR_TOKEN_EXPIRES_AT`, `MICROCOSM_COLLECTOR_ORIGIN`) are set only in part, cannot be read, or name another collector, so such a build stops then too; whether the collector later accepts the credential is not visible to the build. Unset or `0`, builds continue without the emitter as before, and any other value raises `ValueError`. The short-lived Orrery-only emitters are unaffected. Leaving the requirement off (unset or `0`) exists only for the convenience of people outside PolicyEngine who run Microcosm without access to the collector; PolicyEngine's own builds keep telemetry required. Nothing in Microcosm sets the variable yet.
