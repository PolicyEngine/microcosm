A checkpointed US base run (`tools/build_us_puf_support_base.py --stage all`) now runs the 16 steps from `capital_gains_tail_transfer` to `education_inputs_post_clone` in one child process instead of one process per step (decision 1.5 · 6). Every other step still gets a process of its own.

Only the first of the 16 reads its predecessor's checkpoint from disk. Each later step takes the frame the step before it completed, so the 15 reads of a checkpoint of about 2.2 GB, with their SHA-256 and frame identity checks, and 15 process starts no longer happen. Each step still writes its checkpoint, completion record, `stage_profile.json` record and saved check observations, so a stopped run resumes after the last finished step; a resume inside the 16 starts the child at the first unfinished one. Before each step the child still compares the run config with the locked one, as each step process does at its start, so a change to the builder's source files during the run stops it before the next step.

Telemetry still records one stage change per step under the step's name. The child writes each step's name to a pipe as the step starts (`MICROCOSM_US_BASE_STEP_REPORT` names the pipe and the parent's process ID), and the parent records the change, so a failure is recorded against the step that failed. A named `--stage` run by hand still runs one step.

Reading a checkpoint turns NumPy scalars into Python values in object columns and indexes, python-backed `str` columns and indexes, the strata and the strata's index, and a frame handed over in memory keeps them, so the next step could compute on other values. Before a step takes a frame from memory, the child therefore checks those values' types (30 to 117 ms for a post-clone frame's 2.3 million such values) and stops if any would change; the step that left them has completed, so a resume reads its checkpoint. A review of the 16 steps' code found none that leaves such values; no run has shown it.

Two differences between a frame in memory and one read from disk are not checked, since a check could stop a run whose output would be the same: a read gives each missing value in an object column its own NaN object, where a frame in memory may repeat one, and it gives each table's column labels the `str` dtype a new table gets.

What one process gives up: memory is not returned to the system between these steps; on macOS each step's recorded peak memory is the process's peak so far, while Linux keeps a sampled peak per step that includes memory left from earlier steps; and a frame handed over in memory is not read back, so its checkpoint's SHA-256 and identity are next checked when a later process reads the file.

How this was checked, on a small fixture frame: the 16 steps ran in 16 separate step processes and in one child, and every file they wrote (the 16 checkpoints, the run context and the 16 saved observation files) had the same SHA-256. In that fixture 15 of the 16 step functions are stand-ins that write a digest of every value with its type, every dtype, the indexes, the column labels, the strata, the weights, the mass log and the frame metadata, and a floating-point sum of each person's numeric values; `capital_gain_distributions` runs its real code, and the stand-ins evaluate each step's `us/gates.json` check, so the observation files hold entries. A second fixture test compares each frame handed over in memory with what reading the previous checkpoint gives, by value and dtype. The base bit-equivalence test was not run (task 1.5 · 8 was cancelled). Estimated saving (inferred, not measured): about 4 to 6 minutes and 4 to 6 CPU-minutes per Modal base run.
