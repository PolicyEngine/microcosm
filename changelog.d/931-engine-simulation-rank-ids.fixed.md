Each policyengine-uk simulation the UK adapter builds now holds ids that policyengine-core's 32-bit store keeps apart (#931; decision 12, María's rulings of 11 Nov). policyengine-core stores policyengine-uk's five id variables (`person_id`, `benunit_id`, `household_id`, `person_benunit_id` and `person_household_id`) as int32, converting them with numpy's `astype`, which wraps an id outside the type without an error. It builds the entities and memberships from the int64 columns it is given, so two ids that wrap to one value merge no entity: they become one stored key for every formula that reads the id. policyengine-uk 2.174.1 hashes its Warm Home Discount draw on `household_id`, its two Universal Credit deduction draws on `benunit_id` and its birth-month spread on `person_id`. Anything rebuilt from the stored values would see one entity. Within one clone's batch every id carries the same clone offset, so a repeat there needs a copy-layer ordinal on at least one of the two ids.

- **The rule** (`microcosm.frame.adapters.engine_identifiers`, shared, for Max's review). `EngineIdentifiers(stored_dtype)` declares the integer type an engine stores a schema's id and membership columns as. `engine_identifier_tables(schema, tables, identifiers)` hands a simulation the tables it is given when no entity's ids repeat once converted as the engine converts them (`stored_identifier_repeats`). An entity whose stored ids would repeat takes 1 plus each id's rank among that simulation's ids, in id order, and each person's membership of it takes the new id of the group it names, never the 0-based rank (`rank_identifier_tables`, the step that ranks and maps and decides nothing). Ranks are distinct, fit the type and keep id order, so the engine holds every entity's rows in the frame's order, and results still return by position or by the frame's own ids. The frame is never changed. The module also names the entities whose ids the conversion changes (`inexact_identifier_entities`), refuses a request for such an entity's id or membership variable (`refuse_inexact_identifier_requests`, which reads no table unless an id or membership variable is requested), and holds a declaration to an installed engine's types (`require_stored_dtypes`). It reads a schema and entity tables, never a Frame, and names no country. It refuses to renumber an entity that a declared link's table among the tables names, since it maps only the person table's memberships. Its refusals name entities, links, columns, variables and types, never an id or a count. national_frame's release rule keeps its own ranker for now; moving it onto `rank_identifier_tables`, and deriving `UK_ENGINE_IDENTIFIER_MAX` from the declaration, are owed (decision 7).
- **The UK adapter.** `UK_ENGINE_IDENTIFIERS` declares int32, and `_require_identifier_dtypes` checks it against the installed engine's five id variables once per adapter; a test holds national_frame's release range (`UK_ENGINE_IDENTIFIER_MAX`) to the same width. `_dataset_tables` applies the rule to `engine_tables`' tables, and both construction sites build through it, so a call run clone by clone ranks each batch within its own rows. `materialize` refuses, before any engine is built, a request for an id or membership variable whose entity holds an id the engine cannot store exactly, since the engine would return wrapped ids or ranks for it. Each simulation is built with policyengine-uk's `EntityIdWarning` filtered, since the adapter now checks the stored ids itself, and the adapter refuses to build one if policyengine-uk no longer defines that class at `utils.entity_ids`. Building a dataset now builds the adapter's `CountryTaxBenefitSystem` first, which is inert. The stages that call the engine bind the new module beside `microcosm.frame.materialize` (`_ENGINE_COMPUTE_MODULES`), as the walk from the engine the builds inject reaches it.
- **What moves.**
  - Nothing on a frame whose stored ids do not repeat: `UKSingleYearDataset` is built from the same tables, byte for byte, so every engine output is the same.
  - Elsewhere, only that simulation's values keyed on the renumbered entity's ids. For households that is the Warm Home Discount draw, which runs for 2025 to 2030 and adds only to HBAI income, which spine stages request only at 2024. A batched call's id-keyed values can differ from one simulation's over the whole frame wherever either renumbers, since each batch ranks its own rows.
  - The adapter's simulations no longer write `EntityIdWarning` to stderr, and an id request for an entity the engine cannot store exactly is refused; no stage makes one.
  - Every UK graph node re-keys: the kernels that hash the adapter directly, and every other node through its population's version. No other country's keys move. The US annual static-aging manifest's `source_sha256`, which hashes every module under `microcosm.frame`, gains the new file and changes the adapter's entry; it is provenance, not a node key. No declaration, generated file, `gates.json`, schema, receipt or sidecar field changes.
