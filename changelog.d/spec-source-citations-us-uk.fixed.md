Cite source code by symbol, or by line at a named commit, in the US and UK spec packages. A new engine-free guard (`test_spec_source_citations.py`, validators in `test_support/microcosm_build/spec_source_citations.py`) scans every resource in every country package. It refuses a line citation of a file in this repository, pinned or not, including one written as a `PolicyEngine/microcosm` GitHub URL at any ref (`main`, `refs/heads/main`, `feature/x`) or a `microcosm/tools/...` path. It refuses a line citation of any other source unless the citation binds to an inline commit (`commit <sha>`, `at <sha>`, `@<sha>`, or a GitHub `/blob/`, `/tree/`, `/raw/`, `/blame/` or `/commit/` URL): the nearest one in the citation's own clause, else the nearest one before it in its string, unless the citation's clause names a moving ref (`on main`, ``on `main` ``, or a `/blob/main/` or `raw.githubusercontent.com/<owner>/<repo>/main/` URL). A resource's `path`/`commit` mapping pins it too, but only when the cited path ends the pinned path. A commit-like token in no recognised spelling beside a citation is refused as a misspelled pin. So is a line locator after a source name in no recognised spelling (`x.py some_function, lines 12-19`). A truncated hash (`e2de2b41…`) or a hex directory (`at a1b2c3d/foo.py`) pins nothing, and a quoted locator (`x.py:"12-19"`) is a line citation like any other. Each URL is read the way a browser and then GitHub read it first. Its authority is parsed as the WHATWG URL Standard parses it: `\` read as `/`, any number of slashes after `https:` or in a `//host/...` reference, a user and a port dropped, and the host percent-decoded, mapped to ASCII as IDNA maps it and lower-cased, so `%67ithub.com`, `ｇithub.com` and `user@github.com:443` are `github.com`. Then `%` escapes of unreserved characters and `/` in its path are decoded, `.` and `..` segments resolved, and its query dropped, so `%74ools/x.py` and `x.py?plain=1#L12` are line citations of `tools/x.py` and `x.py`. A URL runs to whitespace, so a quote or a bracket in its path or query (`x.py?q='a'#L12`) is part of it. Markdown and prose end a URL at a quote, a parenthesis or an angle bracket, so a string is read that way too where it differs: in `[https://a/?x](https://github.com/...#L12)` the label's query does not hide the link. A string is also read with its Markdown and HTML escapes decoded (`x\.py`, `&#35;L12`): as Markdown decodes them and as HTML does, which leaves a backslash as written (`https:\&#47;github.com` names github.com), each as text and as a URL holds what it decodes to, with references decoded as the HTML standard decodes them. Each reading is also read with its ASCII tabs and line breaks deleted, as the URL Standard reads a URL in an HTML attribute. A quoted attribute value or a Markdown destination in angle brackets that starts a URL is read as the browser follows it, its escapes decoded before its ends are stripped and its spaces percent-encoded, and a URL is read through a Unicode space such as U+00A0, which the URL Standard percent-encodes. A destination in angle brackets is found after the spaces, tabs and one line break CommonMark allows before its `<`. Where a string holds a `?` and a `#`, its URLs are also read through whitespace in their query, which GitHub ignores (`href=".../x.py?a b#L12"`). A citation any reading finds is checked. Every line citation in a string that holds a dot segment (`..` as a whole path segment, either dot perhaps `%2e`) is refused, pinned or not: whitespace, a backslash or markup in the segment it removes can make a renderer remove another one than any reading does, as in `[a]( <https://github.com/.../tools/a b/../x.py#L12>)` or `[a](https://github.com/.../tools/a\b/../x.py#L12)`, where Markdown writes the backslash `%5C`. No resource cites a line in such a string. GitHub reads `%2f` as `/` before it resolves a path, so a `..` beside one is a dot segment too (`tools/a b%2f..%2fx.py`). A string is also refused where any of its readings' sources holds this repository's GitHub path, `PolicyEngine/microcosm/`, with a line fragment (`#L12`) at the first `#` after it, whatever file the link names and whether or not a reading finds the citation. The path is read as GitHub reads one: escapes decoded, a backslash as `/`, a run of slashes as one, `.` segments removed and the owner and name in any case. So a ref holding punctuation (`blob/feature+foo/tools/x.py#L12`), or whitespace before the host where markup has taken an attribute's opening quote (`href="https://a b@%67ithub.com/..."`), no longer hides a link of this repository. No resource holds such a link. A path here can hold an `=` (`docs/.../period=2025-01.json`), so the run of path characters before a cited name is tried as an in-repository path too, and a reverse locator reads a name after an `=` (`lines 3 of a/b=c.py`). An in-repository path's inner `..` segments are resolved (`tools/x/../y.py` is `tools/y.py`).
