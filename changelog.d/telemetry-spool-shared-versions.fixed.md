Checkouts at different microcosm versions on one host keep sharing the local telemetry spool (`~/.cache/microcosm/telemetry/events.sqlite3`). Before, once a newer checkout applied a spool migration, every older checkout's emitter service refused the spool, and its builds ran without hosted telemetry until the checkout was updated.

Spool migrations after the first must now be additive: to a table that already exists they may only append ordinary nullable or defaulted columns and add plain non-unique indexes, never rebuild it, change its rows or give it a trigger. A test holds every packaged revision to that. Each migration also records the spool's lineage, the migrating checkout's history. An older checkout whose head is in that lineage uses the spool as it is, without migrating it or taking the write lock, and services of every version deliver each other's queued events. A checkout whose history diverges from the spool's, such as a branch with a different migration, is still refused in one line. The revision is now read again once the migration lock is held, so an opener that waited while a newer checkout migrated no longer fails with "Can't locate revision".

This covers checkouts from this change on. One from before it still refuses a spool migrated past `20261007_01`, and if it migrates a spool itself it records no lineage, which the next checkout at that revision then records. So the next spool migration should land after this change has reached build hosts, on a branch that includes it.
