After the US repository `policyengine/populace-us` switches to `releases.json`, every US build publishes through the emitter into its own build folder, and this change merges straight after that switch commit (microcosm#1570). The repository has four releases, named in `microcosm.data.contract.US_RELEASES` with the dataset file each new build declares in `US_RELEASE_DATASET_FILES`: `microcosm-us-2024-national` (`national`, the repository's default: calibrated national builds, SPM source enrichments, compatibility recertifications and exact-k builds; `microcosm_us_2024.h5`), `microcosm-us-2024-local` (`local_area`: ACS local-area builds; `microcosm_us_2024_acs_local.h5`), `microcosm-us-2024-receipt-donor` (`national`, never the default: receipt-qualified donors; `microcosm_us_2024_receipt_qualified.h5`) and `microcosm-us-2024-evidence` (`national`, never the default: evidence-tier builds; `microcosm_us_2024.h5`), whose current build takes the place of `latest-evidence.json`. Build IDs keep their `populace-us-2024-…` form, and new calibration weights are `microcosm_us_2024_calibration.npz`. The seven builds the switch moves keep their `populace_us_2024…` names: the `("us", 2024)` registry entry names `microcosm-us-2024-national`, so `microcosm.data.load("us")` reads its current build from `releases.json` (following `latest.json` until the switch) and accepts either dataset name for a listed build (`DatasetSpec.build_folder_filename`). A recertification renames only its H5; the calibration file it carries keeps its parent's name. Every US writer writes `releases/<release>/`, named after the release rather than the build, and rewrites its manifests with `microcosm.data.build_folder_manifests.rewrite_release_dir`; the national builder and the ACS package stage print `publish_command` (`uv run microcosm-publish-release-build <dir> --repo-id policyengine/populace-us --artifact-root <root>`) and `promote_command` (the same with `--promote`), and promoting a national build makes it the US default. The national builder `tools/build_us_fiscal_refresh_release.py` prints `release`, `build`, `release_dir`, `artifact_root`, `publish_command`, `promote_command` and `promotion` instead of `release_id`; its `--release-id` is the build ID and a release name there is refused; each build needs its own `--out`; the release contract runs at publication preflight instead of at the end of the run; and without `--base-h5` a run starts from the national release's current build through `microcosm.data.download("us", 2024)`. The exact-k launcher's receipt carries `release`, `build`, the release directory, `publish_command`, `promote_command`, `promotion`, `automatic_publish: false` and `makes_current: false`, and no tagged command, `publish_argv`, `release_id` or pointer fields. The ACS builder's `package_result.json` gives the release name as `release_id` and adds `release`, `build` and `promote_command`, its `refresh_recipe.publish` is an object `{publish_command, promote_command}`, and packaging twice into one `--out` is refused. The SPM role and receipt donor enrichment builders write their candidates into `releases/microcosm-us-2024-national/` and `releases/microcosm-us-2024-receipt-donor/`, to be certified with `python -m microcosm.data.source_enrichment --certify` and published with `--parent-h5` and `--compatibility-wheel`. The recertification tool's `fetch-parent` takes `--build-id`, and `--release` for a parent in a build folder, in place of `--release-id`, and its `build` takes `--build-id` and prints `release_dir`. A parent or donor in a build folder is named by `repo_id`, `release` and `build`, with its digests and no `revision`; a tag reference (`revision` with `build_id` or `release_id`) stays valid for builds that keep only their tag, and `microcosm.data.build_folder_manifests.referenced_build` says where either is read. `microcosm-publish-release-build` (`microcosm.build.release_publication`) takes the US releases, runs the release contract, or the evidence contract for `microcosm-us-2024-evidence`, refuses a build whose role differs from its release's, takes `--parent-h5` and `--compatibility-wheel` for source enrichments and recertifications, hands a recertification over only once its parent is published with the manifest it carries, and waits up to three hours for a publication; `--preflight-only` checks a build offline. Its `--make-current` and `--promote` refuse a compatibility recertification, which is published without becoming current and loaded with `build=`, as the tagged publisher never pointed `latest.json` at one. Before a preflight or a publication it says a build's recorded compatibility narrowing and claim measurement on stderr, and the preflight's verdict carries them as `narrowed_claims` and `claim_measurement`, as the tagged command did. `microcosm.data.latest_evidence_release` returns the evidence release's current build from `releases.json` when the repository has one, with its folder's paths and `revision` `main`, and reads `latest-evidence.json` otherwise. The tagged publisher (`microcosm-publish-release`, `tools/publish_release.sh`) refuses every US and UK build-folder release and any repository that has `releases.json`, so after both switches no US or UK release publishes with tags or reads the Slack webhook variables, and the dashboard posts US release alerts from changes to `releases.json`. Route A (`tools/route_a/route_a.sh`) looks for its build in `releases/microcosm-us-2024-national` and preflights it with `microcosm-publish-release-build`, and its hand-off record gives `publish_command` and `promote_command` in place of a `tools/publish_release.sh` command.
