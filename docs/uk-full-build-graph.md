# UK full-build graph

The UK has one calibration build. It constructs the canonical FRS spine, which samples at its own rung, gives every household K geographic clones and assigns each clone its area in its own stages. The build then compiles and selects targets on that spine as it stands, constructs the selected contribution matrix, calibrates, optionally selects exactly k households and refits, evaluates gates and diagnostics, and packages a checked H5. It is registered on the shared executable graph (`microcosm.graph`) and served by one driver, `microcosm-build-uk` (`tools/build_uk_full.py`), which carries the release roles of microcosm#823. `--release-role dense` and `--release-role national` both run on the graph, checked by the same posture-aware validator (see "The national role" below). `tools/build_uk_rowwise_candidate.py` is a stub over the driver, so the runbook commands that name it keep working.

**The default is to calibrate all applicable geographies together.** An omitted selector and `--target-geographies all` have the same target scope. `--target-geographies country` explicitly selects country-level rows in the same graph; regional rows are not country-level rows. No failure, size request or performance setting changes the selector implicitly. The spine's geographic clone count K, the exported household count k (`--dataset-households`) and the target scope are independent settings. K is set where the spine is built (the spine command's `--n-clones`); the dense driver's `--n-clones` only asserts it. This registration does not establish native candidate acceptance.

## Run the dense build

From a geography-first spine checkpoint with its `.build.json` and `.spine_gates.json` sidecars:

```bash
uv run --no-sync python tools/build_uk_full.py --release-role dense \
  --input-h5 /data/uk/spine.h5 --input-sha256 <spine-sha256> \
  --ladder /data/uk/ladder.npz --ladder-sha256 <ladder-sha256> \
  --ledger-facts /data/chronicle/uk-artifact \
  --ledger-facts-sha256 <facts-sha256> --ledger-manifest-sha256 <manifest-sha256> \
  --out /data/uk/full-build
```

Build the spine first, with `tools/build_uk_frs_spine.py`, its three conditioned atomic-area supports and its clone count (`--n-clones`, from 1 to 100, one by default). A dense release needs 15 clones, built with `--release-candidate`. The dense build takes K, the sampling and the geography binding from that spine.

`--release-role` is required. The dense role supplies every unset solve default from the local doctrine (epochs, learning rate, seed, weight rule, selection) and refuses the national role's flags (`--target-loss-cap`, `--allow-unpinned-feed`, `--reference-h5` and `--reference-record`). It takes its clone count K, its sampling rung and seed, and its geography binding from the spine it binds, never from a default. An explicit `--n-clones` that differs from the spine's K is refused, naming both. So are a `--sample-fraction` other than 1.0 and any `--sample-seed`: a spine is sampled at its own build. The constituency vintage check retired with `--expected-constituency-vintage` (María's ruling of 2026-11-13). `--ladder` with `--ladder-sha256` is required by the dense role, `--input-sha256` by every `--input-h5` build, and the three Ledger arguments (`--ledger-facts`, `--ledger-facts-sha256`, `--ledger-manifest-sha256`) by every build. The supplied hashes must agree with the committed Chronicle pins: a target-scope filter does not authorise a different source, and the dense role has no unpinned-feed override.

The three atomic-area supports are the spine's inputs, not the dense build's (microcosm#931). The spine's area stages draw on their conditioned forms, which `tools/build_uk_conditioned_area_supports.py` builds from the registered supports (`tools/build_uk_atomic_area_supports.py`; publisher registration PolicyEngine/chronicle#269) and records in `uk/uk_atomic_area_conditioned_supports.provenance.json`. A conditioned support adds each area's deprivation decile, which the draw keeps to, and its households by council-tax band, which the draw weights by. Five spine stages read the three conditioned supports as graph sources: `atomic_area_assign`, `rfdr`, `spi_copy_areas`, `spi_housing_shell` and `council_tax_localise`. Whenever the spine runs `atomic_area_assign`, its command's `--atomic-support-ew`, `--atomic-support-scotland` and `--atomic-support-ni` must name files whose SHA-256 and size are the ones `uk/spec/sources.yaml` registers for the conditioned supports, and the spine refuses any other file before a stage runs. Its build sidecar records how the areas were drawn in a `geography` block: the assignment, the identity column, the definition's SHA-256, the support pins, the draw stream and the register the pins were held to. The dense driver takes no `--atomic-support-*` flag, no support pin and no `--geography-assignment`. Under `--release-candidate` with `--input-h5` it reads the three supports under `--spine-support-ew`, `--spine-support-scotland` and `--spine-support-ni` only to recompute the bound spine's area definition; every other dense build refuses those flags. The legacy sequential ladder draw and `--source-lineage-modulus` are retired.

The dense line's own localisation nodes are retired (microcosm#931): `uk.full.property.value`, `uk.full.property.band`, `uk.full.geography.brma`, `uk.full.private_rent` and `uk.full.geography.rfdr`, with `--property-localisation`, `--brma-localisation`, `--private-rent-localisation`, `--rfdr-localisation`, their six resource flags and their six pins. The spine now does that work on every clone, before the stages that read it, so the dense and national lines both carry what these stages set:

- `local_authority` and `rfdr` set the engine's `local_authority` and `in_rural_fuel_duty_relief_area` from each clone's drawn area.
- `area_brma` takes the retired `frs_brma` stage's place, after `frs_household_draws`. It reads each Great Britain household's BRMA off its drawn area through `uk/brma_area_layer.json`. Northern Ireland has no open BRMA geography, so its households draw from the census counts with `frs_brma`'s keys, seed and salts, and take the BRMA that stage would give them.
- `spi_copy_areas`, after `spi_housing_shell`, gives every SPI copy and income band donor a key and an area of its own, drawn within its region by the households of the band the shell drew (or by all households where the region holds none of it), then its local authority, BRMA and fuel-relief flag. Northern Ireland's copies draw their own BRMA (María's ruling of 2026-11-11).
- `private_rent` runs after the housing shell. It reads each Great Britain private rent off the list of rents of its BRMA (`uk/brma_rent_quantiles.json`), at its rank among the FRS private rents of its region and bedroom size. One scale per FRS region keeps the region's FRS mean rent on the census mix of its BRMAs (`uk/brma_private_rented_households.json`).
- `council_tax_localise` runs just before `was_wealth`. It first keeps each household's paid bill from before it localises (`council_tax_frs_bill`, dropped at release) for the WAS bill predictor. It scales each Great Britain household's council tax by its drawn local authority's 2024-25 Band D over the expected Band D of its draw cell. It reads the bill's provenance, which `frs_council_tax` writes beside the bill (`council_tax_bill_provenance`), to find the households whose gross bill the survey did not give: where the survey gave their band, those FRS households take the 2024-25 statute instead. It moves reductions with the bill, by the same ratio or, on a statute row, by the bill's own change, and caps them at the bill. Northern Ireland, which pays domestic rates, is left as it is (María's rulings of 2026-11-06, 2026-11-13 and 2026-11-14).
- The housing shell prices the council tax of Great Britain's SPI copies and income band donors by the 2024-25 statute at their region's expected Band D, after its band draw, so `council_tax_localise` stays the one step that localises a bill. Northern Ireland's copies keep the bill the shell draws (María's ruling of 2026-11-14).
- `was_wealth` reads each England and Wales owner's main residence off its constituency's knots (`uk/high_value_home_value_knots.json`), at a keyed point inside its weighted slice of its constituency and geographic clone (María's ruling of 17 November 2026), after the chain's second segment (`localise_main_residence_value`). The chain's later draws condition on that value, and `regional_property_uprating` divides by the kept draw, with the factor's mean taken over geographic clone 0, so a frame of K clones keeps the one-clone values for clone 0. The `regional_home_values` stage is retired.

No stage redraws a council-tax band by area: the area draw weights areas by their households in each household's own band instead, and the dense line keeps the spine's bands.

The checkpoint must bind the exact frame content, the current spine stage roster and the gate-report bytes. A spine build records its H5's file digest in the sidecar (`output {filename, sha256, size_bytes}`), in a `<h5>.sha256` file beside it, in its `spine_h5_creation` stage event and in its Logbook `pipeline` verdict (`artifact_sha256`); when the sidecar carries `output.sha256`, the full build refuses an `--input-h5` whose measured digest differs (older sidecars without the key bind by content identity alone). The bound-spine node compares the checkpoint's gate report digests with the branch's own gate declarations and refuses a spine whose gate manifest differs from them, so `--input-h5` needs a spine built by a branch with the same declarations; every acceptance spine on disk when this registration landed predates them and is not admitted. Historical candidate H5 files and reviewed-bypass sidecars are not alternate build sources. Chronicle facts and manifest must match the independently reviewed national and local feed declarations; filtering targets does not relax source validation. Before it pins any input, the dense build reads the bound spine's build sidecar and refuses a spine that is not geography-first. Such a spine lacks a stage `geography_first_roster.GEOGRAPHY_FIRST_STAGES` names, the housing shell's `derive`, `was_wealth`'s `localise_main_residence_value`, or a `geography` block with every key (`spine_posture.require_geography_first_spine`). The check runs again on the authenticated sidecar. The checkpoint holds the sidecar's `geographic_clone_count` to the frame's clone count.

The target registry binds Census household and demographic rows from the reviewed Chronicle feed, including the approved Northern Ireland constituency geography. Geography is assigned in the spine, not in the full build (microcosm#931). `geographic_identity` keys every clone with `geography_household_key`, from its source household, its FRS vintage and its clone path. `atomic_area_assign` then draws each clone's atomic area (E&W 2021 Output Area, Scotland 2022 Output Area, NI 2021 Data Zone) within its FRS region with the shared atomic-geography operator, on a keyed stream: it keeps to the clone's deprivation decile and weights areas by their households in its observed council-tax band, falling back level by level to its region alone. So a clone's draw never depends on row order, K or any other household. It reads every larger geography off the support's mappings. [Geography assignment](geography-assignment.md) states the law. The spine's gates check the draw (see the next paragraph), and the full build places nothing of its own: `uk.full.pool` keeps every row of the spine's version. The OA ladder still supplies the constituency and local-authority rosters, household dispersion and lookup support for target compilation; its household counts are not a second source of calibration targets. The target compilation records the Chronicle identity and the paired ladder digest. The request bindings and the rowwise manifest's `geography.assignment` keep the spine's geography binding, its sidecar's `geography` block with K beside it. So target values and the geography used to assign households can be audited separately.

The spine's gate batteries check the geography. At the assembled boundary, `uk_atomic_area_mapping_integrity` checks the base area draw. At the transferred boundary, the gates check the SPI copies' areas (`uk_spi_copy_area_mapping_integrity`), each later copy's agreement with its parent (`uk_copy_area_agreement`), the BRMA and local-authority engine domains (`uk_brma_enum_domain`, `uk_local_authority_enum_domain`), the geography ladder (`uk_geography_ladder`), the ranking of the localised home values (`uk_stage_area_home_values_ranking`) and council tax reductions within the bill (`uk_council_tax_reduction_within_bill`). The local battery's own BRMA recheck, `uk_local_brma_enum_domain`, retired when the dense line took its areas from the spine.

The request declares existing source adapters and lazy transforms; the spine stages execute in the same graph, and the driver supplies `--spine-h5` when the request omits it. A spine request has no checkpoint H5 to pin, so `--input-sha256` is not required on that path. The spine-only command remains available to materialise an execution checkpoint. The request's `--n-clones`, `--sample-fraction` and `--sample-seed` are the build's K, rung and seed. Its roster is checked as geography-first from the packaged spec before any input is pinned, and again on the spine the build composes. The spine's preparation composes the `geography` block with the helper the sidecar writer calls, so a spine request is bound as a checkpoint's sidecar is. With `--release-candidate`, the spine's gates run at release-candidate strictness, and the request must ask for 15 clones.

For smaller outputs, add `--dataset-households 150000` to use the common informed L0 search, exact-count draw and refit. A sized dense build takes the doctrine's size defaults where the request leaves them unset (microcosm#1124): the exact-count draw at `--selection-pi-hi 0.5`, the refit baseline floored at 0.5 and a chi-square refit L2 penalty toward uniform weights at λ 0.0216 (`--refit-l2-lambda 0` turns it off). At 150,000 households with exactly those settings (microcosm#1124 as amended for microcosm#1301) a sized build can be a release candidate and releasable; any other size stays candidate-only (see the [dense runbook](uk-dense-release-assembly-runbook-762.md#sized-release-microcosm1124)). The size search probes L0 penalties from the doctrine's floor, 1e-10, up to 10, and `--selection-initial-lambda` must lie in that bracket: it is refused, never clamped, outside it or without `--dataset-households`. The bracket is a parameter of the search, draw, refit and holdout nodes, and the size receipt records it as `selection_search_bracket`. `--baseline-pi-floor` floors the inclusion probability the refit's Horvitz-Thompson baseline divides each selected row's dense weight by (0, the default, is the untrimmed baseline), and `--no-size-checkpoint` skips materialising `size_selection_checkpoint.{npz,json}` into `--out`. `--n-clones K` only asserts the bound spine's clone count. With `--dry-run` and `--spine-request`, `--candidate-clone-counts 5,10,15` plans the spine request once per count, as its own `--n-clones`, and prints each compiled operation inventory without solving. It is refused with `--input-h5`, whose K is fixed, and with `--n-clones`. K and k are independent, and neither narrows target scope. A country-only run may bind a spine of fewer clones, but this is never inferred. `--households-only` binds only the Chronicle census-household constituency targets (a target-selection family filter).

The dense line samples nothing of its own. A spine is sampled at its own build: its `--sample-fraction` samples the raw FRS spine at ingest, before enrichment and before the geographic clones. The dense driver refuses a `--sample-fraction` other than 1.0 and any `--sample-seed`, by name. The spine's rung is the build's. It sets the development gate and target-admission policy, the build id carries it, and a release candidate on a sampled spine is refused.

## The national role

`--release-role national` builds the certified national line on the same graph. The driver parses and validates it with the same posture-aware validator (the national role refuses the dense role's arguments, `--release-candidate` among them, and requires a bound `--input-h5` with `--input-sha256`; a `--spine-request` is refused because the national line solves a pinned checkpoint as bound) and composes the national graph (`uk_runtime.graph_national`): `uk.full.spine_checkpoint` admits the bound checkpoint, `uk.full.national_targets` compiles the national register from the pinned Chronicle artifact (measure exclusions, band edges, the frozen-register check, the feed pin with `--allow-unpinned-feed`; no ladder, no local surface), `uk.full.national_problem` refuses non-finite inputs, resolves the engine measures on the bound frame, materialises the register and encodes one ordered problem with the national doctrine's `family_equal` loss weights, mass reason and bounds in its bindings, `uk.full.dense` and `uk.full.calibrated` are the shared calibration nodes under the doctrine's epochs, learning rate and seed (the dense node's admission is the bound spine's provenance artifact rather than a preflight battery, because the national line runs no pre-solve battery: its source and reference gates are the release-cut certifier's), and `uk.full.gates.calibrated` evaluates the seven `UK_CALIBRATION_GATE_SCOPE` gates on the calibrated population. The driver then materialises the seam-shaped evidence from the stored artifacts: the diagnostics through the seam writer with the build block (the digest measured from the file), the target-support sidecars, the calibration-seam battery replayed from the stored phase report and signed (`GateBatteryRun.record_phase`), `microcosm_uk_2024_25.h5`, a graph readback of the written H5 (`uk.full.national.readback`), the schema-1 `build_record.json` that `tools/certify_uk_release_cut.py` certifies, the frozen `national_target_registry.json` and `national_contract_registry.json`, and the schema-4 `rowwise_candidate_manifest.json` (`uk_runtime.national_role`). The Logbook row is on the seam's `uk-frs-calibration` pipeline with the seam's attempt id; staging telemetry, the staged bundle and the end-of-build comparison with the reference (the current national build, microcosm#1095) follow the dense role's switches. A blocked battery leaves the report on disk (`blocked_at_phase: "terminal"`), writes no H5 and records a failed row. The [national calibration runbook](uk-national-calibration-runbook-623.md) and the [national release assembly runbook](uk-national-release-assembly-runbook-806.md) describe the outputs. The in-process calibration seam (`run_uk_calibration`, `UKNationalCalibrationStage`) is retired; its contracts (gate scopes, sidecar authentication, provenance blocks, scoped signing) stay in `uk_runtime.calibration_run`, except the spine and local gate scopes and the scoped gate manifest, which are defined in `uk_runtime.gate_scopes` and re-exported by `calibration_run`. The full gate kernels hash `gate_scopes` in place of the runner, and the preflight's own code leaves the runner out, so in the in-graph build an edit to the runner re-keys only the calibrated gates and what follows them; on a bound spine the checkpoint, whose kernel hashes the runner, still re-keys the preflight and the solve, and on the national line every node. Parity with the seam is a solved question of construction (the same register, the same matrix row for row, the same solver under the same doctrine and seed, the same mass record) checked on the licensed spine.

The national line builds only on a geography-first spine of one geographic clone (microcosm#931). Before it reads any input, the national preparation refuses every build until the degenerate-surface register's `household.atomic_area_basis` exclusion applies on the national line and is in force on `--review-date` (`spine_posture.require_national_exclusion_signed`). The register decides: an entry that applies on the national line and is in force on that date lifts the refusal, and the release cut reads the register again on the day it certifies. The preparation then reads the bound spine's build sidecar, before it pins the input and again once the checkpoint is authenticated. It refuses a spine whose `geographic_clone_count` is not one or whose roster is not geography-first (`spine_posture.require_national_spine`). `uk.full.national_problem` makes the same check before it reads the frame. The national H5 leaves without the three clone-index columns, which are constant at one clone, and with the spine's three area codes under the consumers' names (`constituency_code_oa`, `la_code_oa`, `region_code_oa`); `uk.full.national.readback` expects that export. So a national file carries the spine's areas and the values the spine sets from them. The release certifier (`tools/certify_uk_release_cut.py`) requires the spine's build sidecar to be the one the build record names (`spine_provenance.sidecar.sha256`). Before any gate runs, it checks that sidecar's geography binding at one clone with the helper the dense pre-flight uses (`country_adapter.uk_spine_geography_binding_failures`). It then holds the sidecar's resource and stage artifact pins to the package and recomputes the area definition from the cut's three supports, which it takes under the same `--spine-support-*` flags (`tools/run_uk_cut.py` passes them), so a spine built before a packaged resource changed, or one whose `definition_sha256` names no definition, is refused. It also refuses a candidate that carries a clone index.

## Graph owners and shared contracts

The spine graph is the 63-stage source roster declared by the UK spec, built by `uk_runtime.spine_build` (the spine tool moved into the package; `tools/build_uk_frs_spine.py` is a six-line shim over it). The superseded `frs_hmrc_retained_leaves` and `hmrc_spi_income` stages and the `UK_SPINE_EXCLUSIONS` list that hid them are removed; the active HMRC path is `frs_hmrc_spine_leaves`, `spi_support_channel`, `spi_income_band_donors` and `hmrc_spi_income_spine`, and the FRS HMRC leaf columns come from `uk_runtime.frs_hmrc_source`. The spine's assembled and transferred gate batteries are graph nodes (`uk_runtime.graph_evidence`); stage evidence and fit-weight records are read back from the content store through the shared `stage_evidence` artifact rather than from in-memory collectors; the HMRC replay sidecar is rebuilt from the SPI stage's checkpoint metadata; the spine sidecar records the operation inventory and the graph manifest, and the graph manifest is saved as `spine.graph.json` under the checkpoint root.

The roster is clone-first (microcosm#931). The stages up to `frs_annual_income_spells` run on the survey households. `geographic_expand` then gives every household K geographic clones, each with an equal share of its design weight, and `geographic_identity` keys each clone. Every later stage runs on the clones; [Geography assignment](geography-assignment.md#the-uk-spine) gives the area stages in order. K is a parameter of `geographic_expand`'s graph node: it enters that node's key and every later one, never a stage contract.

The modules under `uk_runtime` divide the roster: `graph_build` composes the graph over the bound spine, `graph_population` owns the pool checkpoint and the population helpers the nodes share, `graph_targets` owns target compilation through the problem, `graph_calibration` owns the dense solve, the size nodes and the calibrated population, `graph_terminal` owns the gate nodes, the holdout, the export and the package, `full_certification` owns the terminal certification node, and `full_build_cli` resolves the request, executes graph endpoints and atomically materialises their stored artifacts.

`operations.json` is generated from the compiled graph, including actual dependencies and artifact owners. It is the execution inventory, rather than a second manually maintained pipeline roster. Composite source/model stages preserve their existing numerical boundary; for example, WAS retains its joint donor/recipient encoding dependency. The graph registration itself changed no imputation order, RNG consumption or clone id. Since microcosm#931 the spine gives every household its geographic clones, keys and areas in its own stages, with keyed draws and copy ids that do not depend on K, and the full build assigns no geography of its own. The sequential ladder draw and `--geography-assignment` are retired.

Shared machinery includes graph execution/storage/replay, typed artifacts, explicit same-kind weight updates, target selection receipts, ordered sparse calibration problem/solution/result codecs, exact-count selection, atomic artifact materialization and bundle publication. UK adapters retain source interpretation, entity relationships, geography mappings, measure bindings and gate prescriptions.

The full target compiler preserves the unreduced band-edge register, reference-period compilations, approved exclusions and frozen-register completeness checks before target selection. A nonempty country-only problem can have zero local rows. Local holdout is then inapplicable, while source, identity, mass and geographic integrity checks remain applicable. Omitted rows are never reported as fitted constraints.

## Engine blocks and spine batches

`--engine-blocks K` resolves `uk.full.measures` with one policyengine-uk engine per clone rather than one over the pool. The count must be one or the spine's clone count K, and any other is refused once the spine is bound, naming K. At every block count, the measures refuse a frame that does not hold the K clones their node binds. Each block's household weights are scaled to the pool's mass. In every simulation the block builds (the measure simulation, its baseline, and the annual-income and counterfactual simulations with theirs), `shareholding` and `consumption_shareholding` are set, at each period the block computes, to the block's own value times `c_b = f_b·S_b/S`; on policyengine-uk 2.179.2, `corporate_land_value` and `consumer_incident_tax_revenue_change` read those shares. That is the block's pool-mass factor times its allocation-key total over the pool's, both from totals the representation records (microcosm#931). Before it sets them, the block checks that its data supplies none of the UK totals the shares would divide by instead (`uk_total_*`, which make a share the pool's already), that the engine's own key total is `f_b·S_b`, and that the engine carries each key and the weights by one factor per year. The annual-income simulation carries other spells by the engine's own growth parameters, so every block uses the same factor. A guard records every formula each simulation runs once the shares are set, and judges policyengine-uk's whole-population formulas against the UK declaration (`microcosm.frame.adapters.policyengine_uk_population`, on the shared `engine_population` machinery). The two share formulas must be the corrected inputs at every period, and `months_since_last_birthday` and `attends_private_school` stored inputs. The engine's income and wealth deciles and relative-poverty flags are refused, and any other such formula that runs must be zero under the parameters checked. Any work in the Universal Credit rebalancing years (2026 on) is refused too, since policyengine-uk draws new-claimant status there by benefit-unit position. The measure step records a violation rather than raising it. Once the blocks ran, `engine_population_representation.exact` holds only if every block applied its correction, passed its checks and got a clean verdict, and `exact_basis` (`pool_share_injection_with_population_guard`) names that basis. The measures then equal one engine over the pool to float32 rounding, not bitwise. An inexact per-block run is not releasable. So while policyengine-uk draws new-claimant status by position, a calibration year of 2026 or later leaves every per-clone run inexact, and so not releasable, and refuses every batched spine call. A block's scratch engine holds no year after the calibration year (microcosm#1615): a measure dated later is refused, and the block computes at no such year. A single block, as on the national line, is exact by construction and records no correction or guard fields.

A spine engine call whose frame carries more than one clone runs one simulation per clone, since one simulation over a cloned spine does not fit in memory. `PolicyEngineUKEngine.materialize` decides from the frame, not from a setting: a call whose household table carries `household_clone_index` with more than one clone runs its simulations in ascending clone order, and each is released before the next is built. Each clone's simulation is built as one over the frame is (`PolicyEngineUKEngine._read_year_simulation`): its dataset is projected to the call's year and no further, and the Universal Credit rebalancing loop stops at that year while it is constructed (microcosm#1615). A frame without the column, or with one clone, takes one simulation as before. A batched call's requests are judged first. A period in the rebalancing years, a refused formula, a frame without `months_since_last_birthday`, or a request for `attends_private_school`, `private_school_vat`, `baseline_private_school_vat` or `gov_tax` before `private_school_attendance` stores attendance refuses the call before any engine is built. Until then the spine's pass lets attendance run only where the three parameters `private_school_vat_rate` reads equal their baseline's and `private_school_vat_change` comes out zero, and only if `gov_tax` does not run. Unlike a measure block, each batch reads the pool's shares at the frame's own weights, unscaled (`c_b = S_b/S`), and is judged under the spine's pass, which raises on any violation rather than recording it, since the values come back as plain arrays. People come back in the frame's order and groups in ascending id order, as one simulation returns them. Each simulation holds the frame's ids where policyengine-core's 32-bit store keeps them apart; an entity whose stored ids would repeat takes 1 plus each id's rank in that simulation's frame, and each person's membership takes the new id of the group it names, so rows keep their order and the frame keeps its ids. Every spine frame from `geographic_expand` on carries `household_clone_index`. On a spine of one clone, as the national line's, every call takes one simulation and batching moves no value. On a spine of K clones, such as a dense release's 15, every call from `geographic_expand` on runs K simulations, one per clone, in as many calls per stage as at one clone. The spine's engine is told K and refuses a frame that carries some of the clones but not all, so no call reads policyengine-uk's shares over part of the pool. One call is a single simulation by design: `spi_copy_areas` reads `LHA_category` for Northern Ireland's SPI copies over a frame without the clone index (María's ruling of 2026-11-11).

policyengine-uk's `attends_private_school` ranks each household's market income plus benefits, less its income tax and National Insurance, over the people a simulation holds, so the `private_school_attendance` stage restates the formula's last step over the whole frame. It computes that income from household-local engine values, ranks it with microdf's `MicroSeries.percentile_rank`, and reads the attendance rates and population factor from the engine's own parameters. Over one simulation it also asks for the engine's flags, stores them once the restatement matches them bit for bit, and raises otherwise. Clone by clone it asks only for the household-local values and stores the restatement. Its evidence records `rank_route` (`engine_with_parity` or `pooled_restatement`) and `engine_parity_checked`. The spine sidecar's `rules_engine` gains `engine_batches`, and beside it `microdf_python`, the microdf-python version whose weighted percentile rank `private_school_attendance` then stores, only on a spine whose calls run clone by clone, and the engine identity does not move with batching. Every stage that calls the engine through the adapter binds the adapter, `engine_population` and `policyengine_uk_population` into its implementation hash, and `microcosm.frame.materialize` and `microcosm.frame.adapters.engine_identifiers`, through which the adapter builds each simulation's dataset and the ids it holds.

An acceptance test runs the H2 fixture's spine through the real engine at one clone and at four (`test_h2_clone_first.py`). It holds the roster's stage count, the clone-index invariant at every node from `geographic_expand` on, and one simulation per clone in each engine call. It runs after merge only, in the `engine-uk-after-merge` job on pushes to main (María's ruling of 2026-11-11).

## Replay and outputs

The shared store defaults to `<out>/.graph-store`. `--graph-store` can reuse another store. `--resume require` requires completed numerical nodes and evidence to be available; output materialization and byte readback still verify the recreated files. `--require-solve-reuse` requires only the solve, so a second release build can re-run the calibrated gates on it (see [a second build that reuses the solve](#a-second-build-that-reuses-the-solve)). `--resume-size-checkpoint` imports a legacy size-search checkpoint only after validating invocation identity, ordered target/household axes, initial weights and recomputed losses. It skips the saved dense solve and search. New runs persist their intermediates as graph artifacts before drawing.

Each attempt also keeps its checkpoint manifests and small stage, gate and provenance reports under `<graph-store>/uk-full-attempts/<attempt-id>`. Its `request.json` carries the request bindings and the attempt's Logbook build id and staging run id (`attempt`). The rowwise manifest's `execution` block records the graph store, the attempt directory, how many graph nodes the attempt reused from the store rather than computed (the first run to reach a node decides), and the earlier attempts on the same store that ran the same request (their directories and ids, the twenty most recent, beside counts of every earlier attempt on the store and of the matching ones), so a resumed build names the attempts whose work it reused; the same counts reach the staging run as a `graph_execution` stage event. The block sits outside the run parameters, so it does not change the candidate identity. A failed run's `failure.json` links to this evidence, including a persisted spine gate verdict before downstream admission stops execution. A previously completed output bundle remains intact.

The output bundle is named from the role's posture and the FRS release vintage: `microcosm_uk_2024_25_local.h5`, its local gate report `microcosm_uk_2024_25_local.local_gates.json`, and the `.diagnostics.json`, `.targets.csv`, `.area_support.csv`, `.holdout.json` and `.target_selection.json` siblings on the same stem, beside `graph.json`, `operations.json`, the stored source/stage/gate evidence and the graph manifests. `candidate.json` is the immutable graph package inventory: it binds the dataset, its evidence, the target selector, the spine's K and the requested k. Comparison inputs refer to this candidate identity. Adding comparison evidence does not rewrite the candidate package. `rowwise_candidate_manifest.json` is projected from the stored artifacts in the schema-4 shape the rowwise tool wrote (`graph_terminal.rowwise_candidate_manifest_from_graph`), so the dense release pre-flight and assembler read a graph build as they read a rowwise-tool build; it records the release role, the release verdict, `staging_delivery` and `staged_dataset`, and the spine's sampling and geography binding (`sampling`, `geography.assignment`). Every area's support figures (rows, ESS and distinct sources) are in `.area_support.csv`, and since María's ruling of 2026-10-26 dropped their withholding (microcosm#1301) the shipped files carry them too: the manifest's `support` block counts the areas checked and below the floor by level and states the minima, the weakest-area and support-limited rows carry them beside `support_below_floor`, and the support gate states an area's figures beside the floors it misses.

The graph evaluates every declared UK gate once; `uk.full.gates.calibrated.gate_report.json` is that full terminal document, the one the package inventory binds (`outputs.full_gate_report`). The local gate report is the six-gate local battery the dense release contract verifies: the driver projects the six `UK_LOCAL_GATE_SCOPE` outcomes from the full document (nothing is re-evaluated; the projection checks the declarations are the same), passes them through the gate battery without raising (the graph's own enforcement still sets the exit status), and writes the report before any refusal, so a blocked candidate leaves it too. Its `release_id` is the Logbook attempt's build id. It is signed when the attempt is bound and `MICROCOSM_UK_TERMINAL_GATE_SIGNING_KEY` holds a 32-byte key; otherwise it is written unsigned, with `signing_error`, and is never shippable. A build whose `--target-geographies` select no local targets drops the local fit claim: it writes no local gate report (`outputs.local_gate_report` is null and `local_gate_report_absence` says why) rather than recording the excluded local gates as not applicable. The Logbook receipts of the six local gates resolve in the local report (`#/gates/<id>`); the other gates' receipts resolve in the full document (`#/report/outcomes/<index>`).

The terminal graph node writes unsigned `certification.json` from those identified artifacts and any declared native or matched-size comparisons. It is non-gating (microcosm#1301): no release step reads it, a scorecard that was not supplied is `not_requested`, one whose identities hold but whose measured limits miss is `diagnostic_failed`, and a holdout that was not requested is not a readiness failure. `build.json` is the completion marker that binds both `candidate.json` and the certification artifact. Physical output bytes are checked against their declared artifacts. Bundle publication writes the completion marker last and rolls back handled failures or interrupts. A process kill or power loss can leave an absent completion marker; a directory without a valid bound marker is not a completed build.

A non-dry dense run is wrapped in the rowwise tool's operational envelope: the Logbook attempt (a `uk-local-candidate` row spooled under `<out>/logbook-spool` on every terminal outcome, chained through `--logbook-prev-row-digest` or `POPULACE_LOGBOOK_PREV_ROW_DIGEST`, with an error receipt on failure), version 3 staging telemetry with the run's sampling evidence (`sample: {"mode": "full"}` on the f100 rung, null below it, judged on the effective fraction), stage events around each graph phase and `calibration_progress` rows for each solve's first and last epoch and every tenth epoch (the rule every build shares, in `microcosm.build.calibration_epoch_telemetry`) from the dense solve and, with `--dataset-households`, the size search and refit (rows tagged with their `phase`), and the staged-dataset delivery of the published bundle under `staged/<run_id>/` in the private repository. `--staging-local-only`, `--no-staging`, `--staging-read-back` and `--no-staged-dataset` behave as in [UK staging operations](uk-staging-operations.md). Dry runs plan without solving or writing and record no Logbook row.

Structural failures stop export. The maintained local statistical failure policy may still export an unreleasable diagnostic candidate with a nonzero process status. Missing evidence remains explicit. `--release-candidate` applies the maintained strictness and solve settings. It requires the UK gate signing key and local targets, because it signs the local gate report, and a spine a release can stand on: unsampled, of the doctrine's 15 clones, built as a release candidate, with a release's geography binding (`country_adapter.uk_spine_geography_binding_failures`). It does not publish or authorize a release. Fixture acceptance proves graph behavior. Measured incumbent comparison evidence is an optional diagnostic supplied with `--native-scorecard` (and, at the requested k, `--matched-size-scorecard`); the certification node verifies their candidate and output identities before recording their assessment.

`tools/build_uk_rowwise_dataset.py` stays the separate driver it was (its tests load it by path, and it still serves `--candidate-clone-counts`). It refuses a clone-first spine at any clone count, so it serves only spines built before microcosm#931. `tools/calibrate_uk_national_dataset.py` was retired by microcosm#823 and does not forward.

## A second build that reuses the solve

A local release is built at most twice (microcosm#1301). Build 1's failing cells and below-floor areas are signed in gate-only registers, and build 2, at the sign-off's head, reuses build 1's solve and recomputes only the calibrated gates, the export, the package and certification: about 1–2 hours rather than 10–16.

**What keys the solve.** Every node keys on its kernel's implementation hash, and the UK kernels' hashes bind the country spec. The nodes the solve depends on bind the *solve fingerprint* (`ResolvedCountrySpec.fingerprint_excluding`, through `uk_runtime.solve_scope.uk_solve_fingerprint`): every packaged UK resource except `UK_GATE_ONLY_RESOURCES`. These are:

- `target_fit_reviewed_exclusions.json` (`uk_target_fit`);
- `local_target_fit_reviewed_exclusions.json` (`uk_local_target_fit`);
- `input_mass_reviewed_exclusions.json` (`uk_input_mass_parity`);
- `local_area_support_exclusions.json` (`uk_local_area_support`), both blocks. The reference generator keeps its own deferred areas and bound families.

The kernels on the solve fingerprint are the target compilation, selection, measures and problem kernels (and the compilation node's `country_contract_sha256`), the source preflight (`uk.full.gates.preflight`, its own kernel `uk.full-gates.preflight@1`), the rotated holdout and the spine gates. The calibrated gates (`uk.full-gates@1`) keep the full fingerprint, so a sign-off re-keys them and everything after them, and nothing before. The degenerate register is solve-scoped, because the release contract pins its digest. `tests/engine_free/uk/test_uk_solve_scope.py` holds the claim from both sides: no target-compile, solve, spine or generator module names a gate-only register, every gate that reads one is a terminal gate, and editing each one leaves every solve kernel's hash unchanged while the calibrated gates' moves. The national graph keeps the full fingerprint.

**Two clocks.** `--review-date` is the solve clock: target compilation and the source preflight evaluate reviewed entries on it, and build 2 repeats build 1's. `--gate-review-date` (default: the solve clock) is the calibrated gates' clock, the date their reviewed exclusions are evaluated on. It may not precede the solve clock and, when given, may not be later than today; it should lie in the range the sign-off draft printed, and with `--require-solve-reuse` it must (see the guard). Only `uk.full.gates.calibrated` carries it, and only when it differs from the solve clock. The export bindings record both (`review_date`, `gate_review_date`). Every register a calibrated gate reads is evaluated on the gate clock, so an entry of a solve-scoped register that a terminal gate also reads must still be in force then.

**The guard.** `--require-solve-reuse` replays the spine and preflight phases, and then the whole solve sub-graph (every strict ancestor of `uk.full.gates.calibrated`: spine, targets, preflight, dense solve, size search, draw and refit, the installed population and the holdout), with `resume="require"` before calibration starts. A miss raises `SolveReuseError` naming the missing nodes, before any of them computes; `failure.json` records it. The calibrated gates and everything after them then run as usual. The flag is refused with `--resume forbid`, and the national role refuses it and `--gate-review-date`. The replay loads the stored pool once more, which costs minutes and memory at K=15.

Three more refusals come before anything runs, so that a mistaken build 2 fails in seconds rather than after the replay:

- without `--graph-store`, or with one that is not a directory: the default store lies under `--out`, and build 2 writes a new `--out`, so the default holds no solve;
- with a gate clock (`--gate-review-date`, else `--review-date`) outside the window of an entry the build depends on: before the `approved_on` or after the `expires_on` of an entry the calibrated gates hold to its window (a gate-only entry on the local line, any `bound_despite_support_floor` approval, a degenerate-register entry on the local line), or after the expiry of a measure exclusion the solve applied, which assembly and upload refuse. The gates would fail such an entry after the replay; the refusal names the entries and the usable range, whose end is the drafter's assembly deadline (both use `rowwise_cli.earliest_expiry`);
- into an `--out` that already holds an attempt: a bundle's `build.json`, which build 2 would replace, or a failed attempt's `failure.json` or Logbook spool row, beside which a retry would spool a second row that `--verify` refuses. As on the national line, this one runs before the attempt opens and writes nothing there; a dry run is not refused.

A solve is reused only when everything that keys it matches build 1:

- the solve code at the commit (build 2 runs at the sign-off's head, whose parent is build 1's commit, and the sign-off changes register data and test pins only);
- `--review-date`, `--release-candidate`, the size, seed, epoch and `--selection-initial-lambda` arguments and `--engine-blocks`;
- every solve-scoped resource;
- the virtual environment (the engine identity and dependency versions) and the platform;
- `--graph-store`, which must be build 1's store.

Build 1 therefore names its solve clock and its store, since the defaults are the day it starts and a store under its own `--out`:

```bash
uv run --no-sync python tools/build_uk_full.py --release-role dense --release-candidate \
  <build 1's inputs and solve arguments> \
  --review-date <YYYY-MM-DD> --graph-store <store> --out <build-1-dir>
```

Build 2, at the sign-off's head, repeats that command with the same `--review-date` and `--graph-store`, a new `--out`, the gate clock and the guard, and replaces build 1's `--logbook-prev-row-digest` with build 1's own row digest, so build 2's Logbook row follows build 1's:

```bash
uv run --no-sync python tools/build_uk_full.py --release-role dense --release-candidate \
  <build 1's inputs and solve arguments> \
  --review-date <build 1's> --graph-store <build 1's store> --out <new-build-2-dir> \
  --logbook-prev-row-digest <build 1's row digest> \
  --gate-review-date <inside the range the sign-off draft printed> --require-solve-reuse
```

A build 1 that took the default store is reused with `--graph-store <build-1-dir>/.graph-store`.

Build 1 itself is not refused into an occupied `--out`, so a failed or interrupted build 1 is retried into a new `--out`, with the same `--review-date` and `--graph-store` so that the retry reuses the nodes the failed attempt finished, and with `--logbook-prev-row-digest` naming the failed attempt's row when it spooled one. A retry into the failed attempt's `--out` would spool a second Logbook row beside the first, and the sign-off drafter, `--verify` and assembly each expect a run directory to hold one attempt; clearing the failed attempt's row instead would drop its Logbook record. The [dense runbook](uk-dense-release-assembly-runbook-762.md#2-run-the-release-candidate) gives the steps.

## Known behaviour changes

Recorded for review in `experiments/901-uk-main-rebase-receipts.md` (R3):

- A blocked *assembled* spine gate fails inside `run_graph` (the first post-checkpoint stage refuses on the stored verdict), and the driver materialises the stored assembled report into `spine_gates.json` (`blocked_at_phase: "assembled"`, the transferred phase `unreached`) before it fails, so the operator gets the same file the previous tool wrote before raising; a blocked *transferred* gate writes the file on the success path. The report is also in the content store either way.
- `numerical_dependencies` pins installed versions into the H2 fixture.
- `_normalise_uk_local_bound_families` keeps main's refusal of a declaration that names nothing; only the graph's country-only target selection (`UKFullProblemKernel`, no local-surface spec selected) passes `allow_empty_local_binding=True` through `prepare_uk_full_solve`, because its local surface is empty by construction.
- The HMRC family names `spi_income_band_donors` (microcosm#1006) as a predecessor and admits its two operation kinds; the contract otherwise refused the drifted operation order.
- `tools/build_uk_rowwise_dataset.py` stays as it was on main (its tests load it by path; it still serves `--candidate-clone-counts`). It refuses a clone-first spine at any clone count, so it serves only spines built before microcosm#931.

Recorded at the review of the national line's move onto the graph (`experiments/901-uk-national-graph-path-receipts.md`):

- The measure-exclusion windows and the target-fit deferral register are evaluated at `--review-date` (default today) on the national line, as the dense graph already did; the retired seam evaluated both at the run clock. A back-dated review date therefore keeps expired exclusions and deferrals in force, which the seam never allowed; the date is a node parameter (`uk.full.national_targets`, `uk.full.gates.calibrated`) and is recorded in the request bindings. The national line keeps one clock: it refuses the dense line's `--gate-review-date` (microcosm#1301).
- An occupied `--out` is refused on the national line with the other argument refusals, before the attempt opens (the seam's `FileExistsError`), so a repeated run never replaces a candidate under the Logbook row that names it and writes nothing into its directory. A `KeyboardInterrupt` records a `discarded` row on both lines and re-raises, as the seam did.
- `build.json` is re-issued after the close step on both lines: the staging receipts are appended to the rowwise manifest and, on the national line, the delivery summary to the build record (the release assembler reads it there), and the completion marker then carries those files' final digests rather than the note that receipts follow.
- The measure receipt records a scratch-mode resolver's `source_path` relative to the per-run scratch root (`simulation-input.h5`), so the measure and national problem nodes are deterministic between identical runs; the receipt no longer carries a temporary directory.
- Under `--release-candidate` the three atomic-area supports must be the `sources.yaml` rows (sha256 and byte size), whatever digest was pinned on the command line, and `tools/preflight_uk_local_release_candidate.py` refuses a manifest whose `geography.assignment` is not the atomic law on those same pins (microcosm#932, round 1). Since microcosm#931 the supports are the spine's inputs: the spine command holds them to the conditioned register, and the dense build's preparation and the pre-flight hold the spine's geography binding (`geography.assignment`) to a release's with one helper, `country_adapter.uk_spine_geography_binding_failures`. A dense release candidate also holds the bound spine's recorded `resource_pins` and `stage_artifact_pins` to the current package, and recomputes its `definition_sha256` from the three supports it reads under `--spine-support-*`.

The dense parity build through this driver was measured at the 10 % rung before microcosm#901 merged (receipts R7); the national line's parity with the retired seam is measured on the licensed spine in the receipts of the change that moved it onto the graph.
